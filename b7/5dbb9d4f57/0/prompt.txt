# Overview: two parallel registries + one dispatch field

There are **two** flat-name-keyed maps, and both have exactly one entry per flat tool name:

- `TOOL_REGISTRY: dict[str, ToolEntry]` — `src/autobio/core/registry.py:47`. `ToolEntry` (registry.py:24-44) holds `image_tag, category, requires_gpu, gpu_count, input_schema, output_schema, default_timeout, supports_batch, description, version, notes, input_format`. **It does NOT store the runner class or any mode/variant field.**
- `TOOL_RUNNERS: dict[str, type[ToolRunner]]` — `src/autobio/tools/__init__.py:32-79`. Maps each flat name to a runner class. `get_runner()` (tools/__init__.py:83-103) instantiates `runner_cls(tool_name, config)`.

The base `ToolRunner.__init__` (`tools/base.py:35-44`) stores `self.tool_name` and `self.entry = TOOL_REGISTRY[tool_name]`. **All variant dispatch happens inside `prepare_workspace`/`parse_output` by reading `self.tool_name`.** `write_config(config)` serializes the dict to `config.json` (`core/workspace.py:59-60`).

So today, adding a "mode" means: add a `TOOL_REGISTRY[name]` entry, add a `TOOL_RUNNERS[name]` entry, and add a branch keyed on `self.tool_name` inside the runner (or a new runner class).

# Pattern inventory (for your refactor)

**A. One runner class, N flat names, dispatch via a module-level dict keyed on `self.tool_name`:**
- `RosettaRunner` — `_VARIANT_CONFIG` (4 names), key = `protocol`/`binary`
- `EvoEF2Runner` — `_VARIANT_CONFIG` (3 names), key = `command`
- `ComplexaRunner` — `_VARIANT_CONFIG` (3 names), key = `variant` (+ per-variant `ckpt_name`)
- `OpenMMRunner` — `_VARIANT_CONFIG` (3 names), key = `protocol`; **also switches input+output schema** and category
- `AntibodyLMRunner` — `_MODEL_CONFIG` (12 names, pairs duplicated) + suffix check; key = `mode` (pll/embedding); **switches output schema**
- `ESMRunner` — `_ESM1B_CONFIG`/`_ESM2_CHECKPOINTS`, dispatch via `self.tool_name == "esm1b"` + `extra["checkpoint"]` (2 names)

**B. One runner class, dispatch via plain string equality (no config dict):**
- `FreeSASARunner` — `self.tool_name == "freesasa_bsa"` (2 names), key = `mode` (bsa/sasa)

**C. Separate runner class per flat name (no in-class `self.tool_name` dispatch); differ in schema AND category:**
- ESM-IF1: `ESMIF1Runner` + `ESMIF1ScoreRunner`, `mode` literal design/score
- AntiFold: `AntiFoldRunner` + `AntiFoldScoreRunner`, `mode` literal design/score

**Cross-cutting inconsistencies worth normalizing during the refactor:**
1. The container-facing "which mode" key has **no common name**: `mode` (antibody_lm, freesasa, esm_if1, antifold), `protocol` (rosetta, openmm), `binary` (rosetta), `command` (evoef2), `variant`+`ckpt_name` (complexa), and **nothing** for ESM (folded into `model_name`).
2. Only **Complexa** sends explicit per-variant `checkpoint` (`ckpt_name`/`ae_ckpt_name`). AntibodyLM sends `model_name`; ESM resolves `extra["checkpoint"]` → `model_name` and drops the raw key. Rosetta/EvoEF2/FreeSASA/OpenMM have no weights.
3. Image-per-mode varies: **one image, many modes** (esm, evoef2, complexa, freesasa, esm_if1, antifold); **one image per mode** (rosetta, openmm); **image per model but shared across the model's two modes** (antibody_lm).
4. `extra` handling splits into two camps: single-class runners use `_CONSUMED_EXTRA_KEYS` filtering; the four separate-class runners (esm_if1, antifold) use unfiltered `config.update(input_data.extra)`.
5. Schema variance across modes exists only in **OpenMM** (single class) and **ESM-IF1/AntiFold** (separate classes) for input+output; **AntibodyLM** varies only the output schema. All other multi-name runners keep one input+output schema across modes.</result>

## 1. CLI (`src/autobio/cli/`)

The CLI is Typer-based. `main.py` wires up six commands and — importantly — triggers tool registration via a side-effect import.

`src/autobio/cli/main.py:7-25`:
```python

...
app.command("list")(list_tools_cmd)
app.command("info")(info_cmd)
app.command("run")(run_cmd)
```

### `list` / `info` / `run` / `result`

- **`list`** (`src/autobio/cli/list.py:13-25`): thin wrapper; calls `list_tools(category=...)` then `format_tool_list(tools, fmt)`.
- **`info`** (`src/autobio/cli/info.py:13-26`): `get_tool(tool)` (KeyError → exit 1) then `format_tool_info(tool, entry, fmt)`.
- **`run`** (`src/autobio/cli/run.py:17-71`): see below.
- **`result`** (`src/autobio/cli/result.py:14-34`): builds a `Workspace(workspace_dir)`, checks `workspace.result_path.exists()`, calls `workspace.read_result()`, then `format_workspace_result(run_result, fmt)`.

### How `info` produces JSON (exact code path)

`info_cmd` → `format_tool_info` in `src/autobio/cli/formatters.py:77-107`. The `model_json_schema()` call is here:

```python
def format_tool_info(name, entry, fmt=OutputFormat.TABLE) -&gt; str:
    input_schema = entry.input_schema.model_json_schema()   # &lt;-- line 88

    if fmt == OutputFormat.JSON:
        data: dict[str, object] = {
            "name": name, "category": entry.category.value,
            "image_tag": entry.image_tag, "requires_gpu": entry.requires_gpu,
            "gpu_count": entry.gpu_count, "default_timeout": entry.default_timeout,
            "supports_batch": entry.supports_batch, "version": entry.version,
            "description": entry.description, "input_schema": input_schema,
        }
        if entry.input_format:
            data["input_format"] = list(entry.input_format)
        if entry.notes:
            data["notes"] = list(entry.notes)
        return json.dumps(data, indent=2)
```

`model_json_schema()` is called unconditionally at line 88 (used by both JSON and TABLE paths — the table renders it at `formatters.py:127`). Only the **input** schema is emitted; `output_schema` is never surfaced by `info`.

### How `run` loads `--config` and constructs the input model

`src/autobio/cli/run.py:41-71`:
```python
config_data = json.loads(config.read_text())          # OSError/JSONDecodeError -&gt; exit 1
autobio_config = AutobioConfig.resolve()
runner = get_runner(tool, autobio_config)             # KeyError -&gt; exit 1
input_data = runner.entry.input_schema.model_validate(config_data)  # any Exception -&gt; exit 1
output = runner.run(input_data, gpu=gpu, timeout=timeout, output_dir=output_dir)  # AutobioError -&gt; exit 1
output_dict = output.model_dump(mode="json")
typer.echo(format_run_result(output_dict, fmt))
```

Key mechanics: the input model is built by `runner.entry.input_schema.model_validate(config_data)` — the whole config JSON is validated against the tool's `input_schema` (a `BaseInput` subclass). Note `run` resolves the runner **first**, then validates via `runner.entry.input_schema` (not via `get_tool`). `gpu` is passed through as a raw string (e.g. `"auto"`, `"0,1"`); the runner's `_resolve_gpu` interprets it.

### What `list --format json` outputs per tool

`src/autobio/cli/formatters.py:42-53` — exactly five keys per tool, sorted by name:
```python
{"name": name, "category": entry.category.value, "gpu": entry.requires_gpu,
 "version": entry.version, "description": entry.description}
```
Note: `gpu` is a bool (not `requires_gpu`), and `input_format`/`notes`/`image_tag`/`gpu_count`/`supports_batch`/`default_timeout` are NOT in the list output — those only appear in `info`.

### Is the CLI ML-heavy or registry-reads-only?

**Registry-reads-only.** No ML libraries are imported anywhere in `src/autobio/` — `grep` for `torch`/`numpy`/`transformers`/`tensorflow` returns nothing. The `import autobio.tools` in `main.py:7` loads all runner modules, but those modules (e.g. `mpnn.py:13-24`) only import stdlib (`json`, `shutil`), `pydantic` schemas, the registry, and `ToolRunner`. Runners shell out to Docker via `python-on-whales`; all heavy compute lives in the containers. So importing the CLI just populates `TOOL_REGISTRY` and `TOOL_RUNNERS` dicts.

```python
heavy_chain: str | None = None   # VH
light_chain: str | None = None   # VL

@model_validator(mode="after")
def _at_least_one_chain(self) -&gt; AntibodySequence:
    if self.heavy_chain is None and self.light_chain is None:
        raise ValueError(f"Sequence '{self.id}': at least one of heavy_chain or light_chain is required.")
```
`AntibodyInput` (`antibody.py:41-65`) carries `sequences: list[AntibodySequence]`, plus optional `layer: int | None` and `pooling: str | None`.

### How generic sequence input is typed today

Plain `dict[str, str]` (chain/seq-id → sequence), in multiple places:
- `EmbeddingInput.sequences: dict[str, str]` — `embedding.py:15`
- `StructurePredictionInput.sequences: dict[str, str]` — `structure_prediction.py:15`
- `ScoringInput.sequences: dict[str, str] | None` — `scoring.py:17`
- `SimulationInput.sequences: dict[str, str] | None` — `simulation.py:38`
- `InverseFoldingOutput.native_sequence` / `DesignedSequence.sequence` also use `dict[str, str]`.

So antibody tools use a structured `list[AntibodySequence]`, while everything else uses the untyped `dict[str, str]`. This is the divergence a refactor would likely target.

### How `extra: dict[str, Any]` is used

Defined once in `src/autobio/schemas/base.py:30-36`:
```python
extra: dict[str, Any] = Field(default_factory=dict,
    description="Tool-specific parameters passed through to the container. "
                "Keys and values are forwarded as-is into config.json.")
```
Runners read tool-specific params out of `extra` and flat-merge them into `config.json`, excluding a per-runner `_CONSUMED_EXTRA_KEYS` set. Examples:
- `rosetta.py:85-87` consumes `{"mutations","chains","chains_to_move","resfile","nstruct","score_function"}`; merge loop at `rosetta.py:150-152`.
- `antibody_lm.py:38` consumes `{"per_position"}`; merge loop at `antibody_lm.py:240-242`.
- `esm.py:102-104` merge loop; `baddg.py:82` / `stabddg.py:83` read `extra["chains"]`; `chai.py:81` reads `extra["chai_fasta"]`; `openmm.py:282` reads `extra["n_steps"]`.

### Do any schemas promote fields beyond `extra`?

Yes — several Input schemas add first-class typed fields on top of `BaseInput.extra`, rather than routing everything through `extra`:
- `structure_design.py:21-39`: `input_structures`, `design_specs: dict[str, dict[str, Any]]`, `n_batches`.
- `inverse_folding.py:15-34`: `structure_path`, `chains_to_design`, `num_sequences`, `temperature`, `fixed_positions`.
- `binding_affinity.py:20-34`: `structure_path`, `heavy_chain`, `light_chain`, `antigen_chains`.
- `protein_binding_affinity.py:22-40`: `structure_path`, `chain_selection`, `temperature`.
- `antibody.py`, `embedding.py`, `scoring.py`, `simulation.py`, `structure_prediction.py` all promote `sequences`/`structure_path` etc.

So the pattern is mixed: stable, category-level params are promoted to typed fields; tool-specific knobs stay in `extra`. Note `simulation.py:13-35` documents ~20 common `extra` keys (temperature, pressure, force_field, etc.) purely in the docstring — they are NOT promoted to fields.

### Does anything use `json_schema_extra`?

**No.** `grep -rn "json_schema_extra" src/ tests/` returns zero hits. No schema currently attaches JSON-schema metadata via `json_schema_extra` (or `model_config`/`ConfigDict` extras).

## 3. `utils/sequences.py`

Pure-Python, no deps. Alphabet constants at `sequences.py:14-17` (`AMINO_ACIDS`, `ANTIBODY_AMINO_ACIDS` = standard + `BOUXZ`, `DNA_BASES`, `RNA_BASES`).

- **`parse_fasta(path: Path) -&gt; dict[str, str]`** (`sequences.py:26-58`): opens the file, strips lines, skips blanks, treats `&gt;`-prefixed lines as headers (leading `&gt;` stripped), concatenates multi-line sequences. Returns insertion-ordered `{header: sequence}`.
- **`write_fasta(sequences: dict[str, str], path: Path) -&gt; None`** (`sequences.py:61-72`): writes `&gt;{header}` then wraps sequence at `_FASTA_LINE_WIDTH = 80` (`sequences.py:23`) chars per line.
- **`validate_protein_sequence(seq: str) -&gt; bool`** (`sequences.py:80-82`): `len(seq) &gt; 0 and set(seq.upper()) &lt;= AMINO_ACIDS`.
- Also present: `validate_antibody_sequence` (`:85-91`, allows `BOUXZ`) and `validate_nucleotide_sequence(seq, molecule="DNA")` (`:94-105`).

### How runners call `write_fasta` to stage sequences

Only two runners use `write_fasta`, both writing the `dict[str,str]` straight into the workspace `inputs/` dir, then referencing the container-internal path in `config.json`:

- `src/autobio/tools/esm.py:89`:
  ```python
  write_fasta(input_data.sequences, workspace.inputs_dir / "sequences.fasta")
  ...
  "input_fasta": "/workspace/inputs/sequences.fasta",   # esm.py:94
  ```
- `src/autobio/tools/esmfold.py:63`: same pattern.

Antibody LM runners do NOT use `write_fasta` — because their input is `list[AntibodySequence]`, `antibody_lm.py:213-222` serializes to `sequences.json` (list of `{id, heavy_chain, light_chain}`) instead. Structure/complex runners (rosetta, chai, mpnn, etc.) `shutil.copy2` structure files rather than writing FASTA (e.g. `rosetta.py:125`). So FASTA staging is only for the two protein-sequence embedding/folding tools that take `dict[str,str]`.

## 4. Tests structure

General layout: `tests/unit/` (60+ files, mocked) and `tests/integration/` (one per tool, real containers). Shared fixtures in `tests/conftest.py:14-30` (`tmp_workspace`, `sample_config`, `monkeypatch_no_gpu`).

### `tests/unit/test_registry.py`

Tests the registry data model, not real tools. Defines local `_MockInput`/`_MockOutput` (BaseInput/BaseOutput subclasses) and a `_make_entry()` helper (`test_registry.py:21-45`). An **autouse fixture `_clean_registry`** (`:143-150`) snapshots `dict(TOOL_REGISTRY)`, clears it, yields, then restores — so tests run against an empty registry. Asserts:
- `ToolCategory` values/count (6 members) and that members are `str`.
- `ToolEntry` construction, `notes`/`input_format` default to `()` and populate correctly.
- `get_tool` success + KeyError messages ("Unknown tool", lists available, `(none)` when empty).
- `list_tools` returns all / filters by category / returns a copy (mutation doesn't leak into `TOOL_REGISTRY`).

### `tests/unit/test_cli.py`

Uses Typer's `CliRunner` (`test_cli.py:18`) to invoke `app`. Same `_MockInput`/`_MockOutput`/`_make_entry` + `_clean_registry` autouse fixture (`:69-75`). Test classes: `TestListCommand`, `TestInfoCommand`, `TestResultCommand`, `TestRunCommand`, `TestImagesCommand`, `TestPullCommand`, `TestHelpOutput`. Assertions are **structural, not snapshot** — e.g. `json.loads(result.output) == []`, `parsed[0]["name"] == "mock-tool"`, `"input_schema" in parsed`, exit codes. `run` tests patch `autobio.cli.run.get_runner` and hand back a `MagicMock` runner with `.entry.input_schema = _MockInput` and `.run.return_value = mock_output` (`:208-227`), and verify gpu/timeout forwarding via `mock_runner.run.call_args.kwargs` (`:280-283`). `images`/`pull` tests patch `autobio.cli.images.ContainerManager`.

### Variant-dispatch tests: `test_antibody_lm.py` and `test_rosetta.py`

Both build the real runner with Docker/GPU patched, then assert the dispatch produces the right `config.json`.

- Runner construction helper (identical shape in both), e.g. `test_antibody_lm.py:34-39`:
  ```python
  def _make_runner(tool_name, config):
      with (patch("autobio.tools.base.ContainerManager"),
            patch("autobio.tools.base.GPUManager")):
          return AntibodyLMRunner(tool_name, config)
  ```
- **antibody_lm** dispatch is keyed on `self.tool_name` → `_MODEL_CONFIG` (`antibody_lm.py:56-187`) and `_is_pll_mode()` = `tool_name.endswith("_pll")` (`antibody_lm.py:255-257`). Tests parametrize tool_name → expected model_name / model_family / chain_separator (`test_antibody_lm.py:128-203`), assert `mode` embedding vs pll (`:156-170`), per-model layer bounds (currab 33, balm 24, ablang2 12, antiberta2 16 — `:337-397`), cache paths (`:408-437`), and registration: every one of the 12 tools maps to `AntibodyLMRunner` in `TOOL_RUNNERS` and has the right input/output schema (`:605-663`).
- **rosetta** dispatch is keyed on `self.tool_name` → `_VARIANT_CONFIG` (`rosetta.py:46-81`). `test_rosetta.py:85-87` derives its parametrization lists directly from `_VARIANT_CONFIG.keys()` and the `requires_mutations` flag. Tests assert per-variant binary/protocol/nstruct/xml_path, `extra` merge vs consumed keys, DDG mutation/resfile handling, and that all four tools map to `RosettaRunner`.

Both dispatch mechanisms are runtime dicts inside the runner module — there is no per-variant subclass. A refactor changing tool_name→config mapping must keep these dicts (`_MODEL_CONFIG`, `_VARIANT_CONFIG`) and the `TOOL_RUNNERS` table in `tools/__init__.py:32-79` in sync.

### Snapshot-style tests of `info`/`list` JSON?

**None.** No syrupy/`.ambr`/snapshot fixtures exist (the only "snapshot" hits are the registry snapshot/restore fixture comments). `info`/`list` JSON is checked by asserting individual parsed keys, primarily in `tests/unit/test_formatters.py` (`TestFormatToolList` `:88-122`, `TestFormatToolInfo` `:130-251`). Notably `test_formatters.py:131-139` asserts `parsed["input_schema"]["properties"]` contains `"sequences"` — i.e. it inspects the `model_json_schema()` output structurally. If a refactor changes schema field names or the `model_json_schema()` shape, these are the assertions that will break.

### General pattern: how unit tests mock Docker/GPU

Two layers:
1. **Constructor-level** (most common): patch `autobio.tools.base.ContainerManager` and `autobio.tools.base.GPUManager` as context managers around runner instantiation (`ToolRunner.__init__` creates `self._container` / `self._gpu` at `base.py:43-44`). Used for prepare_workspace / parse_output tests that never launch a container. Seen in `test_antibody_lm.py:35-38`, `test_rosetta.py:36-39`, `test_tool_runner.py:92-102`.
2. **Behavior-level** for full `run()` lifecycle (`test_tool_runner.py:264-454`): the fixture (`:89-103`) installs `MagicMock` for both managers, sets `mock_gm.allocate.return_value = [0]`; individual tests set `runner._container.run.side_effect = fake_container_run`, where `fake_container_run` writes a `result.json` into the workspace (`_write_success_result`/`_write_failure_result` at `:235-261`) and returns a `ContainerResult`. This exercises prepare → run → read_result → parse_output → metadata without Docker. GPU release, temp-workspace cleanup, and timeout-forwarding are all verified via mock call assertions.

There is also `tests/conftest.py:26-30` `monkeypatch_no_gpu` which patches `autobio.core.gpu.GPUManager._discover_gpus` to return `[]` for tests that want the real GPUManager with no devices. CLI tests instead patch at the `autobio.cli.*` import site (e.g. `autobio.cli.run.get_runner`, `autobio.cli.images.ContainerManager`).

## Refactor-relevant summary

- The single `model_json_schema()` call that powers `info` JSON is `formatters.py:88`; nothing consumes `json_schema_extra` yet, so adding it to fields is a safe, additive way to enrich `info` output.
- Generic sequence input is untyped `dict[str,str]` in 4 Input schemas; antibody input is the only structured (`list[AntibodySequence]`) representation — the natural unification target.
- `extra` is the universal passthrough; each runner defines `_CONSUMED_EXTRA_KEYS` and flat-merges the rest into `config.json`. Promoting an `extra` key to a real field requires adding it to `_CONSUMED_EXTRA_KEYS` too (or it will double-write).
- Variant dispatch = tool_name-keyed dicts inside runner modules (`_MODEL_CONFIG`, `_VARIANT_CONFIG`) + the `TOOL_RUNNERS` map in `tools/__init__.py`; kept in sync by parametrized registration tests.
- Tests are structural (no snapshots); the fragile spots for a schema refactor are `test_formatters.py` (asserts `input_schema.properties.sequences`) and the parametrized dispatch tests in `test_antibody_lm.py` / `test_rosetta.py`.</result>
